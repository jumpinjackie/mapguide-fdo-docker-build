# Agent Instructions for mapguide-fdo-docker-build

## Overview

This repository is a docker (or podman) driven build system that builds MapGuide Open Source and Feature Data Objects (FDO) inside distro-targeted build containers.

It is a **virtual monorepo**: a single git repository that orchestrates the build of two externally-versioned source trees. See [CONTEXT.md](./CONTEXT.md) for the glossary of terms used throughout this document.

## Repository model

### Durable vs. generated content

Durable content (edited and committed to git):

- Top-level `*.sh` build and utility scripts
- `templates/**` — distro templates and container scripts that generate Dockerfiles
- `test/**` — `httpyac` integration test suites (`*.http`)
- `docs/**` — MapAgent OpenAPI spec (`openapi.yaml`, `swagger.html`)
- `patches/**` — patches applied to the source trees
- `dbs/**` — docker-compose fixtures for database-backed tests

Generated content (never hand-edited; gitignored):

- `docker/**` — Dockerfiles and `snap.sh` scripts generated by `env_setup.sh`
- `fdo_version.sh`, `mapguide_version.sh` — generated by `env_setup.sh`
- `build_area/**`, `caches/**`, `artifacts/**`, `sdks/container_download/**`, `logs/**`

When changing build behavior, edit `templates/**` and/or the top-level scripts, then re-run `env_setup.sh` to regenerate `docker/**`. Never edit the generated Dockerfiles directly.

### Source trees

The two source trees are Subversion (SVN) working copies, **not** git submodules:

| Path | Product | SVN branch |
|------|---------|-----------|
| `mapguide/MgDev` | MapGuide Open Source | `branches/4.0/MgDev` |
| `fdo` | Feature Data Objects | `branches/4.2` |

Rules for working with source trees:

- You may edit files under `MgDev` and `fdo`, but you must **never commit changes upstream**. Do not run `svn commit` or any svn command that writes changes back to the repository.
- `svn update` / `svn info` are fine — `svn_update.sh` is the canonical way to update both trees.
- Both trees track their current release branches. The MapGuide 4.0 branch has diverged significantly from `trunk`; those changes will eventually be merged back into `trunk`. `svn_checkout.sh` currently checks out `trunk` for both trees and is intentionally left as-is — if a fresh checkout lands on `trunk`, switch to the intended branch manually (for example `svn switch https://svn.osgeo.org/mapguide/branches/4.0/MgDev mapguide/MgDev`).
- Both source trees compile as **C++11** (`CMAKE_CXX_STANDARD 11` in each tree's top-level `CMakeLists.txt`). See [CPP_STYLE.md](./CPP_STYLE.md) for code guidelines.
- `add_submodules.sh` / `remove_submodules.sh` are placeholders for a hypothetical future where the upstream SVN repositories are migrated to git. They do not work yet — do not use them.

## Requirements

- A Linux host with Docker or Podman. `container_engine.sh` prefers Podman when both are installed; every script resolves the engine through it.
- Git and Subversion.
- Node.js — for the `httpyac` integration test suites.
- `makeself` cloned at `~/makeself` — required by `make_installer.sh`.

## Common workflows

### 1. Checkout sources

```
./svn_checkout.sh
```

Mind the branch caveat in [Source trees](#source-trees).

### 2. Set up the build environment

```
./env_setup.sh --target fdo --distro ubuntu --tag 22.04 --cpu x64
./env_setup.sh --target mapguide --distro ubuntu --tag 22.04 --cpu x64
```

This generates Dockerfiles and `snap.sh` scripts under `docker/x64/<target>/<distro_label>/`. `env_setup_all.sh` does this for every supported distro.

### 3. Build

```
./build_thin.sh --target fdo --distro ubuntu --tag 22 --cpu x64
./build_thin.sh --target mapguide --distro ubuntu --tag 22 --cpu x64
```

FDO must be built before MapGuide — MapGuide consumes the FDO SDK tarball from `artifacts/`. `build_all_thin.sh` builds every supported distro.

### 4. Test

See [Testing](#testing).

### 5. Package the installer

```
./make_installer.sh ubuntu 22 Release
./make_installer.sh generic "" Release
```

or `./make_installer_all.sh` for all combinations.

## Testing

There are two levels of tests:

1. **Unit/integration tests inside build containers** — `env_test_thin.sh` (thin) or `env_test.sh` (build image) dispatch `templates/scripts/container/run_fdo_tests.sh` / `run_mapguide_tests.sh`. `env_test_thin.sh` attempts to recreate the author's ad-hoc testing inner loop, but **may be flaky**. When debugging, prefer ad-hoc commands inside an interactive build container (`./build_thin.sh ... --interactive`).
2. **HTTP API suites** — `test/*.http` are `httpyac` request files run against a live MapGuide server (started via `mapguide_image_install.sh`):

   ```
   cd test
   npx httpyac *_api.http --all --bail --output headers
   npx httpyac post_install_checks.http --all --bail --output headers
   npx httpyac _teardown.http --all --bail --output headers
   ```

`docs/openapi.yaml` is the source of truth for the MapAgent HTTP API (derived from the C++ handler registry in `HttpRequest.cpp::InitializeStaticData()`). Any `.http` test you add or edit must stay aligned with it.

## Code style guidelines (shell)

1. **Container engine** — source `./container_engine.sh` and use `$DOCKER_CMD` (plus `$DOCKER_RUN_EX_ARGS`, `$DOCKER_VOLUME_OPT`, `$DOCKER_RUN_AS_ROOT_ARGS`). Never hardcode `docker` or `podman`.
2. **Argument parsing** — `while [ $# -gt 0 ]` + `case "$1"` + `shift`. Options that take a value consume `$2` and shift again.
3. **Output indentation** — use the `indent()` helper (`sed 's/^/    /'`) and pipe verbose tool output through `| indent`.
4. **Error handling** — no `set -e`. Use explicit checks: `check_build()` or `if [ "$?" -ne 0 ]` after each build invocation, then `exit 1`.
5. **Naming** — `FDO_VER_MAJOR/MINOR/REL/REV`, `FDO_VER`, `FDO_VER_TRIPLE`; same shape for `MG_VER_*`. `BUILD_CONF` is `Release` or `Debug`. `distro_label` is `distro` + major tag (`ubuntu22`) or `generic`. `cpu_label` is `amd64` or `i386`.
6. **Shebangs** — new scripts use `#!/bin/bash`. Keep existing `#!/bin/sh` scripts POSIX-compatible unless you are already editing them.

## Common patterns

- **Generation** — `env_setup.sh` writes a `Dockerfile` and copies the matching `snap.sh` into `docker/<cpu>/<target>/<distro_label>/{run,develop_thin,build}`. Edit `templates/**`, then regenerate.
- **Image layering** — `run` (base + runtime deps) → `develop_thin` (build deps, no source) → `build` (build steps baked in; `ADD`s the FDO SDK tarball, `atomic.h`, and the binary-stripping script).
- **Distro overrides** — a `templates/distros/<distro>/<name>_<distro_label>.txt` (or `install_<distro>.sh`) is picked up automatically and falls back to `<name>.txt`. Examples: `cmd_prepare_mapguide_develop_ubuntu22.txt`, `args_fdo_build_generic.txt`, `dockerfile_x64_mapguide_build_<label>.txt`.
- **Thirdparty libraries** — `generic` builds internal copies; `ubuntu22` uses system packages. See the matrix tables in `README.md`.
- **Version scripts** — `fdo_version.sh` and `mapguide_version.sh` are generated by `env_setup.sh` from `svn info` and are gitignored. Never hand-edit or commit them.

## Validation (definition of done)

- **Shell/template-only changes** — run `bash -n` (or `sh -n`) on every touched script. If `templates/**` changed, re-run `env_setup.sh` and review the regenerated Dockerfiles.
- **Source-tree changes (`MgDev` or `fdo`)** — a run of `./build_thin.sh` against the **baseline distro** is the required validation. The baseline distro is the latest Ubuntu version supported by the build scripts (currently 22.04).
- Full builds are expensive and are not required for every change — use them only when build logic changed or as verification for source-tree edits.
- Before committing or pushing, re-run the validation relevant to the files you touched.

## Known issues

- **ASLR/ASAN on Ubuntu 22.04 hosts** — set `sudo sysctl vm.mmap_rnd_bits=28` before building; see `README.md` for details.
- **WSL2** — use Docker Desktop; Rancher Desktop is not suitable.
- **`env_test_thin.sh` may be flaky** — prefer an interactive build container for debugging.
- MapGuide has not been tested on Ubuntu versions older than 22.04.
- 32-bit (`x86`) Linux builds are not supported.
- `make_installer.sh` requires `makeself` at `~/makeself`.
