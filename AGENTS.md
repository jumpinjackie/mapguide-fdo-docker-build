# Agent Instructions for mapguide-fdo-docker-build

## Overview

This repository is a docker (or podman) driven build system that builds MapGuide Open Source and Feature Data Objects (FDO) inside distro-targeted build containers.

It is a **virtual monorepo**: a single git repository that orchestrates the build of two externally-versioned source trees. See [CONTEXT.md](./CONTEXT.md) for the glossary of terms used throughout this document.

Read [CPP_STYLE.md](./CPP_STYLE.md) before writing FDO or MapGuide code: it is the ownership contract behind the memory-leak rules below, and nearly every defect an agent has introduced in the source trees was a **lost counted reference**.

## Current cycle

**API/ABI mode: `freeze`** — scope `fdo`, `mapguide`; baseline fdo r8386, MgDev r10218. Change this line when the cycle changes (`freeze` | `additive` | `free`); the rules for each mode are in [Policy gate](#policy-gate-which-mode-are-we-in), and a task may override the line for its own duration.

## Repository model

### Durable vs. generated content

Durable content (edited and committed to git):

- Top-level `*.sh` build and utility scripts
- `templates/**` — distro templates and container scripts that generate Dockerfiles
- `test/**` — `httpyac` integration test suites (`*.http`)
- `docs/**` — MapAgent OpenAPI spec (`openapi.yaml`, `swagger.html`), the memory-leak records (`fdo-core-memory-leaks.md`, `fdo-provider-memory-leaks.md`, `mapguide-memory-leaks.md`), the exit-teardown record (`fdo-exit-teardown.md`) and `INNER_LOOP_PAIN_POINTS.md`
- `patches/atomic.h` — the header the MapGuide `snap.sh` scripts copy into the build tree
- `dbs/**` — docker-compose fixtures for database-backed tests

Generated content (never hand-edited; gitignored):

- `docker/**` — Dockerfiles and `snap.sh` scripts generated by `env_setup.sh`
- `fdo_version.sh`, `mapguide_version.sh` — generated by `env_setup.sh`
- `build_area/**`, `caches/**`, `artifacts/**`, `sdks/container_download/**`, `logs/**`

When changing build behavior, edit `templates/**` and/or the top-level scripts, then re-run `env_setup.sh` to regenerate `docker/**`. Never edit the generated Dockerfiles directly.

### Source trees

The two source trees are Subversion (SVN) working copies, **not** git submodules:

| Path | Product | SVN branch |
|------|---------|-----------|
| `mapguide/MgDev` | MapGuide Open Source | `branches/4.0/MgDev` |
| `fdo` | Feature Data Objects | `branches/4.2` |

Rules for working with source trees:

- You may edit files under `MgDev` and `fdo`, but you must **never commit changes upstream**. Do not run `svn commit` or any svn command that writes changes back to the repository.
- `svn update` / `svn info` are fine — `svn_update.sh` is the canonical way to update both trees.
- Both trees track their current release branches. The MapGuide 4.0 branch has diverged significantly from `trunk`; those changes will eventually be merged back into `trunk`. `svn_checkout.sh` currently checks out `trunk` for both trees and is intentionally left as-is — if a fresh checkout lands on `trunk`, switch to the intended branch manually (for example `svn switch https://svn.osgeo.org/mapguide/branches/4.0/MgDev mapguide/MgDev`).
- Both source trees compile as **C++11** (`CMAKE_CXX_STANDARD 11` in each tree's top-level `CMakeLists.txt`). See [CPP_STYLE.md](./CPP_STYLE.md) for code guidelines.
- `add_submodules.sh` / `remove_submodules.sh` are placeholders for a hypothetical future where the upstream SVN repositories are migrated to git. They do not work yet — do not use them.
- `patches/pending.patch` is a **scratch destination for a `svn diff` dump, not a durable artifact**. `svn diff`, run from the FDO tree root, is piped into it so the whole change set can be read in a text editor before `svn commit`, and the file is deleted afterwards. It sits under `patches/` but, unlike `patches/atomic.h`, it is neither committed to git nor gitignored, so it shows up in `git status` until it goes. Write it when the user asks for the change set to review; otherwise leave it alone — do not keep it in step with the working copy, and never describe it in a commit message (see [Commit messages](#commit-messages-one-scope-per-repository)).

### Source of truth and history

The local SVN working copies are the only source of truth — `fdo/` and `mapguide/MgDev`. Search and read them in place (grep, glob, LSP).

- The GitHub repositories `jumpinjackie/fdo` and `jumpinjackie/fdo_cmake` are **unofficial by-products of abandoned SVN→Git experiments**. They are not authoritative, may be stale or divergent, and must **not** be used as a point of reference or cited for behaviour, capabilities or history.
- For history, query the working copy with the read-only SVN commands instead of any mirror: `svn log [-l N] [-r REV] path`, `svn blame`, `svn diff -r A:B`, `svn cat -r REV path`, `svn info`. Never `svn commit` (see the rules above).
- The sibling [mapguide-fdo-build-windows](https://github.com/jumpinjackie/mapguide-fdo-build-windows) repo builds these same upstream branches from its own working copies. A source fix made here reaches that repo by `svn update` once it is committed upstream (the user commits; you never do — see the rules above), or by applying the same diff there while it is still uncommitted; what must not happen is the fix being re-derived independently in the other repo. Do not treat `patches/pending.patch` as the transport — it is scratch (see [Source trees](#source-trees)).

### Commit messages: one scope per repository

A single change set here can span two version control systems with two independent histories — this
git repository, and the SVN working copy (or copies) inside it — so a commit message is written for
one of them and must **not** mention files the other one owns:

| The changed files are under | They are committed to | The message covers |
|-----------------------------|-----------------------|--------------------|
| `fdo/**`, `mapguide/MgDev/**` | the SVN working copy | only those paths |
| anything else git tracks — top-level `*.sh`, `templates/**`, `test/**`, `docs/**`, `patches/atomic.h`, `dbs/**` | this git repository | only those paths |

- An **SVN** commit message describes **only** what `svn status` / `svn diff` report inside that one
  working copy. Run `svn diff --summarize` from the working copy root (`fdo/` or
  `mapguide/MgDev/`) before writing a word of the message, and cover every path it lists. Do not add
  a section for a path that is not on that list — a `Docs:` bullet for `docs/`, or a `Scripts:`
  bullet for a top-level `.sh`, is wrong even when the files are part of the same piece of work.
- The converse holds: a **git** commit message must not describe edits under `fdo/` or
  `mapguide/MgDev`. `/fdo/` and `/mapguide/MgDev` are gitignored, so git has no record of them and
  they are not part of any commit you can make here — those edits are committed with `svn commit`,
  after the user has reviewed the `svn diff` dump.
- `patches/pending.patch` is a copy of the very diff the message describes, so it must never appear in
  the message — it is not a path in either change set.
- The git-tracked files most often mistaken for source-tree content are the `docs/**` pages that
  describe source-tree fixes (`docs/fdo-core-memory-leaks.md`, `docs/fdo-provider-memory-leaks.md`,
  `docs/generic-rdbms-framework.md`) and `patches/atomic.h`, which the MapGuide build consumes. They are
  committed to git, so none of them belongs in an SVN commit message.
- Verification evidence — the suites and configurations a change was tested with, and the before/after
  test and leak totals — is a claim about the change rather than a file, and is always welcome in the
  message. Take the subject and body conventions from that history's own recent messages (`svn log`
  for the working copy), including how tickets are cited (`#<ticket>`, `Fixes #<ticket>`).

## Running commands inside build containers

A "thin" build container is a disposable, distro-specific toolchain: a compiler, the libraries for
one distro, and whatever SDKs the build installs. Everything durable lives on a mounted host volume
— the source tree (`/tmp/work/src`), `build_area/`, `sdks/`, `caches/`. Working inside one therefore
mutates nothing that outlives the container *except the source tree*, which is the point when you
are making source changes.

So **before running any build, test or verification command in a container, look for a running
interactive build container and `exec` into it** rather than starting a one-shot container:

```
. ./container_engine.sh
$DOCKER_CMD ps --format '{{.ID}}  {{.Image}}  {{.Status}}  {{.Names}}'
```

`build_thin.sh --interactive` does not pass `--name`, so the container name is auto-generated (for
example `jolly_johnson`); identify the container by its **image** instead:

| Image | What it is |
|-------|------------|
| `fdo_<distro_label>_develop_thin_<cpu>` | FDO thin build container |
| `mapguide_<distro_label>_develop_thin_<cpu>` | MapGuide thin build container |
| `<target>_<distro_label>_build_<cpu>` | A build-image container |

Then run commands in it:

```
$DOCKER_CMD exec <id> bash -lc 'cd /tmp/work/build_area/fdo && cmake --build . --target ...'
$DOCKER_CMD exec <id> bash -lc '/tmp/work/scripts/build_mapguide_incremental.sh'
```

The container already has the mounts at their `/tmp/work/...` paths, the engine's user and SELinux
settings applied, a warm ccache at `/tmp/ccache`, and often FDO already installed under
`/usr/local/fdo-4.2.0` — so no `--userns=keep-id --user 0`, no `:z`, and no re-install.

A container that has already run a build has FDO installed; a **new** one does not, and that is the one
piece of container state a MapGuide build cannot do without — the build tree fails at once with
`'/usr/local/fdo-4.2.0/lib64/libExpressionEngine.so', needed by ..., missing and no known rule to
make it`. `/tmp/work/scripts/build_mapguide_incremental.sh` installs it (idempotently, stamped
against the SDK tarball) before building, and `run_mapguide_tests.sh` does the same via its
`--prepare`. Do not "fix" this by rebuilding the whole tree with `build_mapguide.sh`, and do not
copy an installed FDO between containers.

Three things to keep in mind:

- Debug and Release are **separate containers and separate build trees**. Check
  `ls /tmp/work/build_area` and exec into the container whose build configuration matches what you
  need; that is usually the tree the user is already working in, so you validate the same artefact
  they will. They are also different runtimes, so never install or copy a library between them — see
  [Same source is not the same runtime](#same-source-is-not-the-same-runtime).
- An edit under `Oem/**` (the internal GEOS, for example) is **not** picked up by
  `build_mapguide_incremental.sh`. `cmake_bootstrap.sh` copies each OEM tree into
  `build_area/oem/<name>` and builds that copy, so the incremental loop has to be handed the file
  explicitly — copy it into the matching `build_area/oem/<name>` path and `make` there before the
  MapGuide build, or the change silently does nothing and a fix looks like it had no effect.
- Container state is not precious. If you change something other than the source tree (installed
  FDO, files inside the container, environment variables), that is no big deal — the container is
  disposable and can be killed and recreated in its place. Do not let caution about its state push
  you into spinning up a parallel one-shot container, or into skipping validation.
- Stopping the host-side command does **not** stop what it started in the container: a killed
  `$DOCKER_CMD exec ... ./UnitTest...` usually leaves the suite running, creating and dropping
  datastores behind you. Before trusting a fixture state, or a "clean" run you just started, check
  `ps -eo pid,cmd | grep UnitTest` inside the container and kill the PID there. Likewise a suite that
  stops consuming CPU with a log that is not growing is waiting on the database (buffered stdout makes
  it look frozen); a wedged `dbs` instance reports "delay in prelogin response" and has to be
  recreated rather than restarted.

With no running container, a one-shot `run --rm` is a fine fallback — see
[Verifying a leak fix](#verifying-a-leak-fix) for the mount, install and `LD_LIBRARY_PATH` recipe.

## Common workflows

### 1. Checkout sources

```
./svn_checkout.sh
```

Mind the branch caveat in [Source trees](#source-trees).

### 2. Set up the build environment

```
./env_setup.sh --target fdo --distro ubuntu --tag 22.04 --cpu x64
./env_setup.sh --target mapguide --distro ubuntu --tag 22.04 --cpu x64
```

This generates Dockerfiles and `snap.sh` scripts under `docker/x64/<target>/<distro_label>/`. `env_setup_all.sh` does this for every supported distro.

### 3. Build

```
./build_thin.sh --target fdo --distro ubuntu --tag 22 --cpu x64
./build_thin.sh --target mapguide --distro ubuntu --tag 22 --cpu x64
```

FDO must be built before MapGuide — MapGuide consumes the FDO SDK tarball from `artifacts/`. `build_all_thin.sh` builds every supported distro.

### 4. Test

See [Testing](#testing).

### 5. Package the installer

```
./make_installer.sh ubuntu 22 Release
./make_installer.sh generic "" Release
```

or `./make_installer_all.sh` for all combinations.

## Testing

There are two levels of tests:

1. **Unit/integration tests inside build containers** — `env_test_thin.sh` (thin) or `env_test.sh` (build image) dispatch `templates/scripts/container/run_fdo_tests.sh` / `run_mapguide_tests.sh`. `env_test_thin.sh` attempts to recreate the author's ad-hoc testing inner loop, but the FDO path **may be flaky**. When debugging, prefer ad-hoc commands inside an interactive build container (`./build_thin.sh ... --interactive`) — and if one is already running, `exec` into it instead of starting another (see [Running commands inside build containers](#running-commands-inside-build-containers)).

   For MapGuide, the inner loop is `/tmp/work/scripts/build_mapguide_incremental.sh` (FDO SDK + `atomic.h`, then `mgserver` and `MgUnitTesting` only) followed by `run_mapguide_tests.sh --component <name>`; the details, the `LD_LIBRARY_PATH` it sets and the pass/fail rules are in [README.md § 4.4](./README.md#44-the-mapguide-rapid-inner-loop).
   `mgserver test <component>` executes an `MgTestCommand`, so `MgServer::svc()` returns before the
   accept handlers, the client/admin/site operation-thread pools and `ACE_Reactor` — the path a real
   server takes is covered only by `run_mapguide_tests.sh --run-mode` (below) and by the installer
   smoke test. Use `--run-mode` when the change is in `Server/src/Core`, the accept handlers or
   `MgThreadBase`/the thread pools; it needs no packaged `.run` and fails on a shutdown hang, a
   non-zero exit, a missing `Server stopped` marker and any LeakSanitizer summary.

2. **HTTP API suites** — `test/*.http` are `httpyac` request files run against a live MapGuide server (started via `mapguide_image_install.sh`):

   ```
   cd test
   npx httpyac *_api.http --all --bail --output headers
   npx httpyac post_install_checks.http --all --bail --output headers
   npx httpyac _teardown.http --all --bail --output headers
   ```

`docs/openapi.yaml` is the source of truth for the MapAgent HTTP API (derived from the C++ handler registry in `HttpRequest.cpp::InitializeStaticData()`). Any `.http` test you add or edit must stay aligned with it.

An `mgserver test` run can also **pass and still exit non-zero, or hang, during process teardown** — the assertion
summary is printed before shutdown runs. Judge a suite by its `All tests passed` / `assertions:` line and always
run it under a timeout; do not treat the exit code alone as the result. See
[docs/fdo-exit-teardown.md](./docs/fdo-exit-teardown.md).

## Debugging memory leaks (ASan/LSan)

Debug builds are ASan/LSan-instrumented, so every FDO provider unit-test runner's log doubles as a
LeakSanitizer report. The per-leak record, the before/after totals and the technique notes live in
[docs/fdo-core-memory-leaks.md](./docs/fdo-core-memory-leaks.md) (FDO Core) and
[docs/fdo-provider-memory-leaks.md](./docs/fdo-provider-memory-leaks.md) (providers) — add a row for
every fix and keep their status tables current.

The MapGuide server's `mgserver test all` run is instrumented the same way, and its record is
[docs/mapguide-memory-leaks.md](./docs/mapguide-memory-leaks.md); the per-leak table there is kept
current the same way. Run it through `run_mapguide_tests.sh --component all`, judge it by the Catch2
summary, and note that **a single-suite run is not a smaller `all` run**: shutdown runs once per
process, so `--component <one suite>` additionally exposes exit-time thread races that the aggregate
hides (that is how the stranded `ACE_Log_Msg` records in
[docs/mapguide-memory-leaks.md](./docs/mapguide-memory-leaks.md#the-ace-allocations-that-only-appear-in-a-single-suite-run)
showed up). Use single-suite runs to attribute a family, and `--component all` as the number you
report.

Two triage tools earn their keep on this tree: `ASAN_OPTIONS=fast_unwind_on_malloc=0` when the fast
unwinder stops inside `libstdc++`/`libxerces`/`libACE` and the record cannot name its owner (the
DWARF unwinder recovered the frames for both the 272 KB wstring and the 190-object Xerces records),
and `/proc/self/task` printed from the end of `main()` when the suspicion is a thread that outlives
teardown.

### Working a new report

1. Read the totals and count both kinds of record before touching any code:
   `grep -E 'OK \(' <log>` / `grep -E '^SUMMARY' <log>` / `grep -c '^Direct leak' <log>`.
   Run the suite yourself first, so the "before" figure is one you measured. A green run that leaks
   still exits non-zero — LeakSanitizer's only way of drawing attention to the report — so never read
   that exit code as a test failure when the log says `OK (<n>)`.
2. Group the **direct** records by their `#1` frame and by the test that appears further down the
   stack. Record families that repeat across tests are the cheapest wins: test-side ownership fixes
   (a raw `FdoPtr` candidate) cost nothing and can remove most of the direct total at once.
3. Then take the largest **indirect** groups. Pick the record with a *direct* sibling in the same
   group if there is one — that record names the lost reference for the whole subtree.
4. Fix in batches, re-run the whole suite, and expect the indirect graphs to collapse once their
   root direct record is gone (the MySQL report went from 359 KB to 46 KB off one 416-byte root).
5. Compare the **sets of record signatures** (the top few frames of each record), not just the totals,
   between the before and after runs: a fix must remove records and add none. That check is what
   caught the parser fix adding nothing new, and what tells "fixed the leak" apart from "shuffled it"
   when a byte total barely moves. Suites the change does not touch must come back with exactly the
   record counts they had before — that is the cheapest, strongest regression evidence there is.
6. **Find the one registry that carries the residue before you instrument anything.** The runner takes
   the registration name as its argument (`./UnitTestSQLServerSpatial initfiletest=<init>
   SchemaMgrTests`), and a whole-suite residue is usually one or two registries: SQL Server Spatial's
   1.7 MB is `SchemaMgrTests` alone (`OK (10)`, 1,842,864 B, ninety seconds against ten minutes), and
   MySQL's and PostGIS's are `FdoApplySchemaTest`. Bisecting by registry costs one run per candidate and
   turns every later iteration — instrument, build, measure — into a minute-scale loop instead of a
   ten-minute one. The registration names are the `CPPUNIT_TEST_SUITE_NAMED_REGISTRATION` strings in
   the provider's `UnitTest` sources, which are not always the class name (`SqlServerSchemaMgrTests`
   registers as `SchemaMgrTests`).

The provider suites are `Providers/GenericRdbms/Src/UnitTest/UnitTest<Target>`; run one with
`./UnitTestMySql initfiletest=<init-file> [SuiteName]` from the build area, where the init file lives
in `templates/scripts/container/test_init/`. Their captured logs are in
`artifacts/Debug/test-logs/<Suite>_unit_test_log.txt`.

Two things about those runs decide whether the figures mean anything. **The harness is shared**:
`Utilities/TestCommon/**` and `Providers/GenericRdbms/Src/UnitTest/Common/**` are compiled into every
RDBMS suite, so a record allocated in shared test code (the silent `catch(...)` in
`FdoSchemaTest::DropDatastore` is one) appears in several suites' logs and one fix clears them all —
check two suites that share the file, and ODBC SQL Server and PostGIS are the cheap ones.
**The run recipe has to match**: `LC_CTYPE=C.UTF-8` (which `run_fdo_tests.sh` defaults and a bare
`exec bash -lc` does not) and a datastore-free instance, or dozens of fixtures fail in `setUp()` and
both the failure set and the record families change — see the "datastore-free instance and a UTF-8
`LC_CTYPE`" entry in [docs/sqlserver-spatial-linux-support.md](./docs/sqlserver-spatial-linux-support.md).

### Reading the report

- `Direct leak` is a chunk nothing points to: a genuine lost reference, and its `#1` frame is the
  allocation site to fix. `Indirect leak` is a chunk reachable from a leaked chunk; its own frames
  are only the allocation path and are usually not the root cause.
- **A rootless reference cycle is reported entirely as indirect records**, so a report with zero
  direct records is not a clean report. Compare both kinds before declaring victory.
- LeakSanitizer follows raw pointers, so one *direct* record can anchor a large indirect subtree. If
  class X can never own class Y, yet Y's members (and what they point at) all sit in X's subtree,
  then X was reached through a raw back-pointer and X itself is the lost reference. That is how a
  single leaked 416-byte owner was found to hold a whole physical schema (~331 KB).
- `LSAN_OPTIONS=report_objects=1` prints the leaked addresses, which is what instrumentation needs to
  match a report record to a live object.
- **Your own tracing registry is a root, so it makes the leak you are measuring disappear.** A
  `std::set<const void*>` (or map) of the objects you are tracing is live global data holding their
  addresses, and LeakSanitizer scans globals conservatively: every traced survivor becomes reachable,
  so do the members it owns, and a 1.8 MB report comes back as zero records. Erasing on destruction is
  not enough — the *survivors* are exactly what stays in the set. Store the addresses **masked**
  (`addr ^ 0x5A5A…`) and unmask on lookup, or keep only a sequence number and print the survivor's
  index; the leak then measures as it did before the instrumentation, and the tracing still names what
  survived. Mask **every** map in the registry, including the one that keeps the object pointer for the
  `atexit` dump — an unmasked copy there silences the report exactly as the address set does, which is
  how a "0 records" reading was produced twice on this codebase before the cause was found. A
  zero-record reading taken from an instrumented build is not evidence of a fix until you have checked
  that no registry, map or static holds an unmasked pointer to the survivors.
- **Count the containers too, not just the objects.** A survivor at `rc == 1` whose creation stack
  points at the wrong code path usually means a *container* is the actual holder: PostGIS's 14 stranded
  tables were held by 7 `FdoSmPhDbObjectCollection`s, and counting those (a two-line ctor/dtor counter
  plus an `atexit` dump) localised the real owner in one run after the reader-chain stacks had misled.
  Dump each live container's parent, size and member names, then capture the containers' creation stacks
  the same way as the objects'.
- **Count live objects one layer at a time and follow the survivors.** Instrument creation against
  destruction for each class in the ownership chain (the pool trick is not needed; a pair of counters
  and an `atexit` dump is enough) and read the survivors as a chain: PostGIS's 92 KB turned out to be
  15 physical db objects, 8 base objects, 1 `FdoSmLpClassBase`, 1 property mapping and 2 object
  properties — each layer holding exactly the layer above it. When the survivor counts line up like
  that, the leak is a closed cycle between a handful of objects and the creation stack of the outermost
  survivor names the code path that built it. A single survivor in a class you did not expect (here an
  *autogenerated* object-property wrapper class that is never added to its schema's class collection) is
  the giveaway that a collection-level collector will never see it.
- **Balanced `AddRef`/`Release` with one reference left does not distinguish an orphan from a cycle.**
  It says only that the surviving holder is a class your instrumentation did not cover. The SQL Server
  Spatial owners had exactly that signature — every traced call balanced, `rc == 1` at exit — and were
  held by a loader class nobody had traced; the physical tables in the same schema manager have the
  same signature and are still unexplained. Widen the instrumentation to the classes that keep that
  type in a counted member (grep for `FdoPtr<T>`/`FdoXxxP m` members, not just the type itself) before
  concluding that a reference is orphaned.
- **A record's stack names the test that allocated it — read that before instrumenting anything.** Split
  the log into records (`Direct leak of N byte(s)` / `Indirect leak of N byte(s)` up to the blank line)
  and pull the `in <Class>Test::<Method>(` frame out of each stack; grouping records by that key and by
  byte total turns a whole-suite report into "everything is in `FdoApplySchemaTest::TestSchema`" in one
  pass, which is how the MySQL, PostGIS and SQL Server Spatial residues were localised with no re-run.
  Two caveats: several records legitimately carry no method frame (the stack is capped at 30 frames, or
  the allocation came from `setUp`/a helper), so report the unattributed count rather than pretending it
  is zero; and the frames *below* the test name still matter, because the 30-frame cap hides the test
  name precisely on the largest records — a 150 KB record whose visible frames are all
  `FdoSmLpSchema::LoadClasses`/`FdoRdbmsDescribeSchemaCommand::Execute` is an entire logical schema
  graph, whatever test allocated it.
- **Pooled objects hide their owner.** FGF geometries and their `FdoByteArray`s are rented from
  thread-local pools, so a geometry whose reference count is one too high is still *reachable* through
  the pool and is never reported; only the separately allocated byte-array buffer shows up, as a
  direct record whose `#1` frame is the constructor that filled it (`FdoArrayHelper::AllocMore` under
  `FdoFgfLineString::Reset`, say). Neither the test frame nor the provider frame in that record is
  therefore where the reference was lost. Follow the *array's* refcount, not the geometry's: the lost
  reference is one AddRef taken on the array somewhere else, and the record disappears when that is
  released.
- Totals drift a little between runs (some buffers leak only on some runs), so judge a fix by whole
  records — especially the direct-record count — not by small byte deltas.

### Generated parsers are checked in — the `.y` is the input, the generated file is what compiles

`Utilities/Common/Src/Parse/yyConstraint.y`, `Fdo/Unmanaged/Src/Fdo/Parse/yy{Filter,Expression}.y` and
`Fdo/Unmanaged/Src/Geometry/Parse/yyFgft.y` are inputs to `build_parse.sh`, which runs `yacc` and the
`script*_linux` sed pipeline (renaming the parser's symbols into the `fdo_constraint_yy`-style
namespace and moving its globals into the shared `FdoCommonParse`), and the **generated `yy*.cpp` is
what is checked into SVN and compiled**. A grammar-rule change therefore has to be accompanied by the
equivalent change in the generated file — do not edit a `.y` and expect the behaviour to change.

Regenerating is not a simple `./build_parse.sh` away: the checked-in Linux parsers are **byacc 1.9**
(FreeBSD yacc) output and the `yy*Win.cpp` ones are **GNU Bison 1.875** output, while Ubuntu 22.04
offers byacc 2.0 and bison 3.8, whose skeletons differ by ~1,000 lines and whose new globals the sed
pipeline does not rewrite. `build_parse.sh` also writes the generated header next to the `.cpp`, but
the checked-in copy lives in `Utilities/Common/Inc/Parse/`. So the working rule is: change the `.y`
(it records the intent, and `FdoCommon.vcproj` regenerates `yyConstraintWin.cpp` from it on a Windows
build), then hand-apply the same change to both generated parsers, keeping the two variants' symbol
numbers straight (byacc numbers nonterminals `314`-`331` here, bison `65`-`82`; the byacc file needed
a `yystos[state]` table added because byacc 1.9 — which has no `%destructor` support — does not emit
one). The `%destructor` work recorded in
[docs/fdo-provider-memory-leaks.md](./docs/fdo-provider-memory-leaks.md) is the worked example.

The parser's error handling is where this bites: the values yacc discards on a syntax error are
released by nothing else, so a leak there needs `%destructor` declarations for the node-producing
nonterminals rather than an edit to `FdoCommonParse::Abort()` (releasing from `Abort()` over-releases
the nodes whose stack reference an action already consumed).

### The FDO idioms that cause almost all of these leaks

- **`SmartCast<T>()` returns a counted reference.** It exists so the result can be handed straight to
  an `FdoPtr`. Using it inline (`obj->SmartCast<T>()->Foo()`) drops that reference and keeps the
  object — and everything it owns — alive. This is the single most common leak in this codebase.
- **Any `FdoXxx*` that comes back from a `Get*`/`Find*`/`Create*` may be a counted reference** —
  `FindItem`, `GetItem`, `FdoFunction::GetArguments`, `GetCharacterSet`, `GetExtent`,
  `GetProviderConnectionObject`, `CreateSchemaManager`, `GetPhysicalSchema`, `GetManager`. Hold it in
  an `FdoPtr`, or release it; never park it in a raw pointer or dereference it inline. A *chain* of
  them (`schemas->GetItem(0)->GetClasses()->GetItem(name)`) drops one reference per link, and
  `SmartCast`-style getters such as `FdoFeatureClass::GetGeometryProperty()` (which returns
  `FDO_SAFE_ADDREF(m_geometry)`) are counted too.
- **`FdoCollection::Add()`/`Insert()`/`SetItem()` AddRef what they are given**, so they do not consume
  the caller's reference: `coll->Add(FdoX::Create(...))` loses the `Create()` reference outright (40 B
  per call), and `coll->Add(ptr)` obliges the caller to release `ptr` itself. Give every `Create()` a
  home: `FdoPtr<FdoX> x = FdoX::Create(...); coll->Add(x);`.
- **`FdoFgfGeometryFactory::GetFgf(geometry)` returns a counted reference to the geometry's byte
  array** — `FdoFgfGeometryImpl::GetFgf()` is `FDO_SAFE_ADDREF(m_byteArray)` for an FGF geometry and a
  fresh array otherwise. Handing it inline to something that AddRefs it in turn — `FdoGeometryValue::Create(...)`,
  `SetGeometry(...)`, `CreateGeometryFromFgf(...)` — drops it. The stranded chunk is then the *array*,
  whose report frames are the ring or polygon that filled it, not the call that dropped the reference,
  so the allocation site in the record is innocent (`FdoRdbmsSchemaUtil::FixGeometryVertexOrder` is the
  worked example). Hold it in an `FdoPtr<FdoByteArray>` and pass that.
- **A counted reference stored in an object whose owner holds it raw is a cycle.** The connection
  holds its capabilities in a raw member, so the capabilities' back-pointer to the connection must be
  raw too. Child-to-parent links are non-owning. The same pair hides in a *loader*: an owner keeps its
  `FdoSmPhSynonymBaseLoader` in a raw member it releases only in `~FdoSmPhOwner`, so a counted
  loader-to-owner reference is unbreakable — the owner's other references all go, the loader keeps it
  at 1, and the destructor that would release the loader never runs. Releasing it earlier is not an
  option, so the back-pointer is what has to become weak. Watch for a derived class **shadowing** a
  weak member its base class already keeps (`FdoSmPhDbObjectComponentLoader::mOwner` is
  `FdoSmPhOwner*` with the comment "Weak reference since an FdoSmPhOwner can own this object");
  `FdoSmPhSynonymBaseLoader` redeclared it as a counted `FdoSmPhOwnerP` and cost the SQL Server
  Spatial suite 1.72 MB.
- **A copy must not own what it was copied from.** `FdoSmLpPropertyDefinition::mSrcProperty` (the
  original of a copy) and `mPrevProperty` (the previous version) were `FdoPtr`s, so every copy owned its
  original; for the autogenerated object-property class — which is deliberately in no collection — that
  closed `wrapper class -> its copy of the property -> the original -> the property mapping -> the
  wrapper class`, a rootless cycle no teardown sweep could reach, and it cost MySQL 24 KB and SQL Server
  Spatial 25 KB. Both are now non-owning pointers and the `Get*Property()` accessors `FDO_SAFE_ADDREF`
  what they hand out. Whenever a member's name is `mSrc…`, `mPrev…`, `mParent`, `mOwner` or `mContaining…`,
  ask which object *owns* the relationship before making it counted.
- **A *cache of dependents kept on the owning side* is a cross-reference, so it must be weak too.**
  `FdoSmPhPostGisTable::mSubDeletedTables` records each derived table in its base table so the drop
  order is right, and it was a counted collection: `base table -> (list) dependent -> (mBaseObjects)
  base object -> (mDbObject) base table`. Clearing the list in `CommitChildren()` fixed the normal drop
  and left the cycle in place for a **schema** drop, because PostGIS drops a whole schema in one
  statement and `CommitChildren()` never runs — so "I clear it on the commit path" is not the same as
  "it cannot outlive". A list that exists only for ordering is a list of weak references; this one is
  now a `std::vector<FdoSmPhDbObject*>` whose owner is the owner's db-object cache, with a duplicate
  guard because `SetElementState` can visit the same dependent twice. When a container's fix works for
  one code path, check the *other* paths that fill it.
- **Any two objects the same container owns must not reference each other by count.** A class's base
  class, an object property's class, a physical table's dependency list (`mSubDeletedTables`) and a
  table's base-object links are all cross-references between siblings, and a sibling pair that
  references each other survives the container that owned them both. When the container is going away
  it can break them (see the class-cycle collector in `patches/fdo_leak_fixes.patch`, which detaches
  only the members nothing outside the container holds); when a *drop* is the only moment the list is
  needed, clear it there (`FdoSmPhPostGisTable::CommitChildren`). Detaching every link unconditionally
  is the trap — it changes what an externally-held sibling sees, and a fixture that asserts on that is
  stating the contract.
- **Empty or nameless catches swallow `FdoException*`** — `catch (...)`, `catch (FdoException*) {}`,
  and `catch (FdoException*) { return; }` all leak the exception and its message. Name it, assert on
  it, then `FDO_SAFE_RELEASE` it. An exception nested as another exception's *cause* is AddRef'd by
  the new exception, so the caught reference itself still has to be released.
- **Constructors and destructors that skip uninitialised state** — a ctor that leaves member slots
  indeterminate plus a dtor gated on `qid != -1`, an open connection or a non-NULL member leaks every
  slot that was never initialised (see `FdoRdbmsPvcInsertHandler`).
- **A constructor that throws runs no destructor** — anything it allocated or AddRef'd before the
  throw leaks; release each member as the constructor goes, in a `catch (...) { ...; throw; }`.
  The same trap applies to a plain factory function: `GetAggregateClassDef()` made its clone with a
  raw `FdoFeatureClass::Create()` and then let `GetExpressionType()` throw for a bad aggregate
  argument, losing the clone and its whole property graph (792 B per bad-aggregate fixture). Hold
  the result in an `FdoPtr` and `Detach()` it on the way out.
- **A container of raw pointers does not release its elements** — `std::map::clear()`, a defaulted
  destructor and a `std::vector<FdoX*>` all leave every element's reference standing; own the
  contents with an explicit release loop, or hold the elements as `FdoPtr` where the container allows.
- **C failure paths that return an error without freeing what they just allocated** — a failed
  `mysql_real_connect` without `mysql_close`, a dropped `new[]` buffer.

`FdoPtr<>` is vetted **only** as a local variable or a class member — never as an STL container
element, parameter or return type. Its semantics: `FdoPtr(T*)` *attaches* (no AddRef), the copy
constructor and `operator=(const FdoPtr&)` AddRef, and `operator=(T*)` releases the old value then
attaches. `FdoIDisposable::Release()` returns the new reference count ("value for debugging use
only"), which is the cheapest leak probe there is: print it at teardown and an object that should be
gone shows `1`.

### The MapGuide idioms that cause the same leaks

`Ptr<>` behaves exactly like `FdoPtr<>` (attach on construction and on `operator=(T*)`), so the same
two mistakes appear on the `Mg*` side. The ownership contract is in
[CPP_STYLE.md](./CPP_STYLE.md#mapguide) and the measured record in
[docs/mapguide-memory-leaks.md](./docs/mapguide-memory-leaks.md); what cleared 648 KB of the server
report was these five shapes:

- **Dereferencing a counted getter inline.** `schema->GetClasses()->GetItem(0)`,
  `layer->GetLayerDefinition()->ToString()`, `envelope->GetLowerLeftCoordinate()->GetX()` and
  `siteConn->Open(MgUserInformation::GetCurrentUserInfo())` each drop one reference. They are the
  same defect, and they differ only in what the lost reference dragged with it: the class collection
  behind `DescribeSchema` was 285 KB of the report (its class definitions, property definitions and
  every string they hold), while the definition id, the `MgCoordinateXY` pair and the users'
  information were 1.6 KB between them. Hold the result in a `Ptr` and use that.
- **Removing the explicit `SAFE_ADDREF` after a `Ptr` assignment.** `m_definition = layerDefinition;`
  attaches the *caller's* reference, so a member which needs its own (the caller keeps its `Ptr`)
  must pair it with `SAFE_ADDREF`. It reads like a double count and is not; deleting it compiles
  cleanly and produces a use-after-free on the next read of the member. Addref'ing a getter's result
  before assigning it to a `Ptr` is the reverse mistake, and that one leaks.
- **A raw `Mg*` local or helper return in test code.** `MgMap* map = new MgMap(...)` leaks the map
  and its layer/resource-content graph (172 KB here). The report then has *no* direct record naming
  the map: `MgLayerCollection` keeps a raw back-pointer to its `MgMapBase` owner
  (`MgLayerCollection(MgMapBase* owner)`), and LSan follows raw pointers, so the leaked group is one
  cycle in which every chunk is reachable from another. Read an all-indirect report as "find the
  owner the stack names", not as "there is no direct leak".
- **Leaving thread-local state set.** `MgUserInformation::SetCurrentUserInfo()` stores into an ACE
  key created with a NULL destructor, so whichever value a thread last set — the main thread at exit,
  or a worker the tests spawn — is never released unless the thread clears it first.
- **`ACE::fini()` running while an ACE thread is still alive.** That thread loses its per-thread
  `ACE_Log_Msg` (4,216 B + a 4,097 B buffer) and `ACE_Thread_Exit` (16 B). `MgThreadBase` therefore
  spawns **joinable** threads: `ACE_Task::wait()` on a `THR_DETACHED` thread returns in 0 us, which
  is why the waits in `MgLogManager::StopLogThread`, `MgServerManager::StopWorkerThreads` and
  `MgServer::svc` were no-ops. Any new long-lived ACE thread must be joinable *and* waited for
  before `ACE::fini()`.

Three library facts sit behind those. Xerces' `createLSSerializer()`/`createLSOutput()` objects are
owned by their caller (`MgXmlUtil::ToBytes()` leaked one descriptor per call). CS-Map
(`Oem/CsMap`) is compiled **without** `-fsanitize=address`, so its C globals are not LSan roots —
a live CS-Map cache reads as leaked and has to be released explicitly (`CSrlsCategories()` from
`MgCoordinateSystemFactory::DeleteCatalog()`, which `MgServer::fini()` now calls). And in the
internal GEOS (`Oem/geos`), an overlay ring builder leaks its partial result when a
`TopologyException` escapes and `SnapIfNeededOverlayOp` then retries, so a *passing* geometry suite
can still be leaking rings; a throwing ring constructor runs no destructor.

The general rule those three share: **release process-lifetime third-party state from
`MgServer::fini()`** (the "orderly clean up applicable static manager objects" block), not from a
static destructor. LSan's check is an `atexit` handler that runs before `__cxa_finalize`, so anything
freed only at static-destruction time is reported as leaked; that is also why the CS-Map catalog
being *reachable* rather than destroyed at teardown was not good enough.

### Instrumentation, when the report cannot name the lost reference

1. Temporarily override `AddRef`/`Release` (plus ctor/dtor) on the suspect class to print `this` and
   a backtrace, gated on an env var, then build and run **one named suite** — CppUnit suites register
   their own name (`CPPUNIT_TEST_SUITE_NAMED_REGISTRATION`), so
   `./UnitTestMySql initfiletest=<init-file> <SuiteName>` runs just that one.
2. With virtual inheritance the traced `this` is offset-adjusted and will not match the malloc address
   in the report. Instead diff the set of ctor addresses against the set of dtor addresses — created
   minus destroyed is the leaked set — then read that object's event history: an object leaked through
   a *lost* reference shows balanced AddRef/Release, but a surviving initial reference.
3. Confirm the provider actually recompiled with the instrumented header (check the build log for the
   translation units) — a stale vtable silently bypasses the overrides.
4. When the suspect is a pooled buffer rather than an object with a vtable, step 1 becomes a trace of
   the *rent/buy-back* points instead: `FdoFgfGeometryPools::GetByteArray()` and
   `TakeReleasedByteArray()`, `FdoFgfGeometryImpl::SetFgf()`/`SurrenderByteArray()`,
   `FdoArrayHelper::AllocMore`/`DisposeOfArray`, and `FdoArray<T>::AddRef`/`Release` (defined in
   `Inc/Common/Array.h`, so a header edit rebuilds only the targets you build). Print the pointer and
   count at each, then print a `backtrace()` **only** when the count is higher than the code path can
   explain — `rc >= 3` for an array handed out of a pool with one owner is what caught the
   `GetFgf()` reference. `backtrace_symbols_fd()` in that inline template yields readable provider
   symbols in a Debug build. The pool machinery itself is not the defect: it hands out a single owner
   reference, and its double-homing (a factory pool entry and the thread-local pool) plus
   `*newArray = *array` in `AllocMore` are consequences of a stray reference, not causes — never
   "fix" a pooled-array report there.
5. Revert the instrumentation before measuring the final numbers.

### Verifying a leak fix

- Run the whole suite in the running Debug container first: `$DOCKER_CMD exec` into it, then
  `cmake --build . --target install` and run the runner from `Providers/GenericRdbms/Src/UnitTest`.
  Only if no interactive Debug container is running, fall back to a one-shot container
  (`--userns=keep-id --user 0`; mount the build area, `logs/test/<suite>`, the source tree, `sdks`
  and `templates/scripts/container`), and read or delete container-written logs through
  `podman unshare`. See [Running commands inside build containers](#running-commands-inside-build-containers).
- With the one-shot fallback, each `run --rm` is a **fresh container**, so the install step is not
  optional and its effect does not carry over: a provider that the suite loads *by name* (SHP opens
  `OSGeo.SHP`, for example) is `dlopen`ed, and the installed `/usr/local/fdo-4.2.0/lib64` has no
  `ld.so.conf` entry, so run with `LD_LIBRARY_PATH=/usr/local/fdo-4.2.0/lib64`. Without it the
  connection manager cannot load the provider, tests fail with an exception whose teardown then
  dereferences a NULL connection and the run dies with an unrelated-looking SEGV in the *test* code.
- Export `NLSPATH` at the build tree's generated message catalogues
  (`NLSPATH=$(pwd)/nls/linux/en_US/%N`, from the build area root) when you run a suite binary
  directly instead of through `run_fdo_tests.sh`, which defaults it itself. Without it every test
  that asserts on message text fails, because FDO resolves the message to its raw symbol
  (`FDOSM_220`) rather than English — it looks like a regression from your change but is purely the
  environment. In the OGR suite that is `TestCase_EvalQuotedIdentifier`,
  `TestCase_SelectBadReaderProperties` and `TestCase_SelectAggregateBadReaderProperties`.
- The SHP suite additionally needs `locale-gen en_US en_US.UTF-8 fr_FR ja_JP.EUC-JP` and its
  `Providers/SHP/TestData` reset, the same way `run_fdo_tests.sh` does, or it reports locale
  failures and stale filesets instead of the real result.
- Build before measuring: `--target install` re-links the runner, and an edit may live in a library
  the suite does not otherwise rebuild (`ODBC`, `SchemaMgr/Ph/Cfg`) — build those targets explicitly
  to prove they compile.
- Confirm the run is still green (`OK (<n>)`), record the before/after totals and the direct-record
  count, and update the matching `docs/*memory-leaks.md` in the same change.
- Record cycles that need a semantic ownership change rather than "fix" them — but *measure* the
  claim first, because "the strong link is load-bearing" is often only true for the naive break. The
  cheap experiment is: detach the cycle's links unconditionally at the owning container's teardown,
  rebuild, and run the suite. If it goes green *and* the records vanish, the cycle is collectable; if
  a fixture fails on an observable property (a refcount, a `GetBaseClass()` after the schema is gone),
  that fixture is stating the contract the naive break violates — and a mark/sweep pass at the same
  teardown point usually satisfies both. Mark roots as the members whose count is not explained by the
  container's own reference plus the links from inside it, follow their links, and detach only the
  unmarked members. See the measured `FdoClassDefinition` result in
  [docs/fdo-core-memory-leaks.md](./docs/fdo-core-memory-leaks.md); the SDF/WFS residues are recorded
  rather than fixed because their anchor is a connection-to-reader reference, not a container.

### Platform locking semantics (`CRITICAL_SECTION` vs `pthread_mutex_t`)

- Win32's `CRITICAL_SECTION` is **recursive** — the owning thread may enter it again — while
  `pthread_mutex_init(m, NULL)` is not. Code that shims one onto the other (`STL_CRITICAL_SECTION`,
  `CriticalSectionHolder` and `ForceLeaveCriticalSection()` in
  `Providers/SQLite/Src/Provider/SltProvider.h`) was written against the Windows behaviour, so a lock
  that an inner call on the same thread takes again (metadata build → `GetMetadata()` → metadata
  build) is free on Windows and a permanent self-deadlock on Linux. When adding a lock to code like
  this, either the POSIX shim must create a `PTHREAD_MUTEX_RECURSIVE` mutex or the nesting has to go;
  FDO ticket #891 (r7133, Windows stability) and FDO ticket #895 (r7150, the Linux deadlock) are the
  same change swapped back and forth over exactly this mismatch.
- Both of the provider's mutexes (`m_csMd`, `m_csStm` in `SltProvider.h`) are created recursive, on
  purpose, for Windows parity — the `STL_CRITICAL_SECTION` shim is meant to *be* a `CRITICAL_SECTION`,
  and every path in the provider has always run against a recursive lock on Windows. The accepted
  consequence is that a same-thread re-entry in the query-cache paths, which used to hang loudly on
  Linux, now proceeds; the lock-hold windows themselves are unchanged, because the
  `ForceLeaveCriticalSection()` calls still release the lock at depth 1. Do not "restore" the plain
  mutex without a concrete failure that requires it.
- A hung suite reports itself: the process is single-threaded, stops consuming CPU and its only task
  waits in `futex_do_wait`. Sample it from inside the same container (`pgrep -x UnitTest`, then
  `/proc/<pid>/status` and `/proc/<pid>/task/*/wchan`) — `$!` after a backgrounded `cmd1 && cmd2` is
  the subshell, not the test process. `stdbuf -o0` makes the partial log name the test it died in,
  but it needs `ASAN_OPTIONS=verify_asan_link_order=0`, because its `LD_PRELOAD` displaces the ASan
  runtime and every run then aborts with "ASan runtime does not come first in initial library list".
- Suite runners load providers *by name* through `providers.xml`, so a unit-test target does not
  depend on the provider library and `cmake --build . --target SQLiteUnitTest` reports "no work to
  do" after a provider edit. Build the library target instead (`SQLiteProvider-4.2.0`) and re-run the
  registry that hung (`./UnitTest SelectTest`).

## FDO API/ABI compatibility

A provider is a separate shared library that the core loads at runtime, so core and providers have an ABI relationship even though they ship from one tree. Most changes under `fdo` cannot affect it — and knowing which ones can is what makes an "is this a breaking change?" question quick to answer.

### What is actually public

The SDK install manifest is the authority; do not infer the public surface from directory names. The shipped include tree (`install_manifest.txt` in the build area) is:

- `Fdo/`, `Common/`, `Geometry/`, `Spatial/`, `ExpressionEngine/`
- the top-level `Fdo.h`, `FdoCommon.h`, `FdoGeometry.h`, `FdoSpatial.h`, `FdoLimits.h`, `FdoMessage.h`, `FdoStd.h`
- `Rdbms/` and the `SDF/`, `SHP/`, `WMS/`, `KingOracle/`, `GdalFile/` provider directories

`Utilities/SchemaMgr/**` and `Utilities/TestCommon/**` are **not** shipped. `SchemaMgr` is built with `add_library(... STATIC)`, so it is compiled into every provider rather than linked from a shared object: its headers are a compile-time boundary only and cannot break a binary swap. The other `Providers/**` headers are not installed either.

The provider↔core contract is a single symbol, `CreateConnection`, resolved with `dlsym` / `GetProcAddress` (see `Fdo/Unmanaged/Src/Fdo/ClientServices/ProviderDef.h`). `_load`/`_unload` were never part of it. On Windows the export mechanism is `FDO_API`/`FDORDBMS_API` = `__declspec(dllexport)`, with no FDO `.def` export lists to keep in step.

### Same source is not the same runtime

A Debug and a Release build of the same source are **different runtimes**, not the same runtime at different speed, so a library copied between them is not a compatibility test:

- Debug is ASan/LSan-instrumented and Release is not. An instrumented provider loaded by a non-instrumented core (or the reverse) is a mismatched allocator and runtime, and ASan insists on being first in the initial library list.
- The two configurations differ in optimisation, and therefore in what the object code expects at a boundary — see the NULL-`this` note in [CPP_STYLE.md](./CPP_STYLE.md).

Keep each tree's `build_area/**` and installed FDO (`/usr/local/fdo-4.2.0`) belonging to the configuration being built, and reinstall FDO in the tree that consumes it rather than pointing one configuration at the other's artefacts. This is the Linux counterpart of the Windows rule that a provider DLL and `FDO.dll` must share toolset and flag flavour (`/MD` vs `/MDd`, `_ITERATOR_DEBUG_LEVEL`).

### Checking a revision range

1. **Source.** `svn diff -r A:B --summarize`, then keep only the paths under an `Inc/` directory. For those, `svn diff -r A:B <paths> | grep -E '^[-+].*virtual'` answers the question that matters most: was a virtual function added, removed or reordered?
2. **Symbols.** Diff `nm -D --defined-only` over the shipped `lib64` of the old and new SDKs. A removed symbol is only a break if something imported it — check for undefined references to it in both the old and the new binaries before reporting one.
3. **Old providers.** Resolve every provider `.so` in the *previous* SDK against the union of the current build's exports. Anything unresolved is a genuine hot-swap break.
4. **Layout.** Compile a `sizeof`/`offsetof` probe against the previous SDK's `include/` and against the current headers, and diff the output. `FdoPtr<T>` holds exactly one `T*`, so an `FdoPtr<X>` member becoming a plain `X*` is size-, offset- and vtable-neutral — as is adding a `static` member function, or an override of a virtual that already exists in a base class. Adding a data member to a class in a *shipped* header is the change that is not safe.

The baselines are already on disk, so this needs no extra build: `artifacts/<conf>/fdosdk-<ver>.<rev>-<distro>-<arch>.tar.gz` names the revision that produced it, and any `build_area/**/_CPack_Packages/**/TGZ/fdosdk-*/` staging tree has the same `include/` and `lib64/`. Windows binaries do not need a Windows host to inspect — `llvm-readobj --coff-exports`, `objdump -p` and `pefile` all read PE exports and imports on Linux.

### Policy gate: which mode are we in?

The mode is the line in [Current cycle](#current-cycle) at the top of this file. Read it before touching anything under `Fdo/Unmanaged/Inc/**`, `Utilities/**/Inc/**`, a shipped provider header, or before removing or renaming anything a shipped library exports — and state the mode you assumed when you report the change.

The mode line's scope covers `mapguide` as well, where the same gate applies to a different surface: not the C++ classes but the SWIG binding interface. What that means, and which edits are the ones the gate is guarding there, is in [MapGuide API/ABI compatibility](#mapguide-apiabi-compatibility).

- **`freeze`** — the maintenance cycle. The [checking a revision range](#checking-a-revision-range) steps are mandatory for any change that could reach the shipped surface, and a change that would break it is escalated, not made: if a task seems to need one, stop and ask rather than reformulating the task so that it avoids the question.
- **`additive`** — still shipping, no longer changing shape. New interfaces, new classes and new non-virtual members are fine. Changing an existing virtual in any way (adding, removing, reordering) is not, and neither is changing a data member of a shipped class: appending a virtual "at the end" still breaks every provider that implements the interface.
- **`free`** — feature development. Change the surface deliberately, but not silently: name the removed or renamed symbols and the changed layouts in the change description, so the baseline can be re-cut. The blast radius is a coordination problem rather than a compatibility one, and it outlives the cycle change — a provider-ABI break invalidates every provider in the SDK, and `mapguide` consumes the FDO SDK tarball from `artifacts/`, so FDO and MapGuide have to be rebuilt and released together.

An explicit instruction in the task ("we are in feature development now, ignore the freeze") overrides the line for that task only; say which one you followed. Only the mode line's *value* is cycle state — everything else in this section is durable guidance and should not be edited to change the mode. The baseline revisions in that line are the ones the frozen surface was taken from when the cycle opened, not the trees' current revision, so they are expected to fall behind as the branches advance; do not "refresh" them.

## MapGuide API/ABI compatibility

MapGuide follows a **looser policy than FDO**, and the reason is what is actually public: nothing links the C++ classes. What reaches an application developer is the SWIG-generated Java, .NET and PHP binding, so the contract is the **binding API surface** plus the correctness of the glue interop library that marshals it onto the C++ objects. As long as the binding surface stays the same and the glue still calls the wrapped C++ APIs correctly, every other consideration is insignificant — a C++ change that would break under [FDO API/ABI compatibility](#fdo-apiabi-compatibility) (a reshaped class, a reordered vtable, a renamed internal) is invisible here, provided the glue is rebuilt against it.

### What is actually public

- **The generated proxy surface** — `org.osgeo.mapguide` for Java, `OSGeo.MapGuide.*` for .NET, the `Mg*` classes for PHP. Compare this, not the C++ headers, when judging whether a change is a break.
- **The glue interop libraries** — `webserverextensions/lib64/libMapGuideJavaApi*.so` and `libphp_MapGuideApi*.so` in the full build, and, for .NET, `lib{Foundation,Geometry,PlatformBase,MapGuideCommon,Web}UnmanagedApi.so` plus the C# assemblies they back.
- **The hand-written managed layer** — `Bindings/src/Managed/DotNet/OSGeo.MapGuide.{Foundation,Geometry,PlatformBase,MapGuideCommon,Web,Portable}` and `MapGuideDotNetApi`, with hand-written types added where the generated proxies are not enough (`Foundation/custom/Streams.cs`, `PlatformBase/custom/MgColor.cs`, `Web/custom/EntryPoint.cs`, and `Common/MgClassMap.cs`'s class-id pairing from `Bindings/src/Tools/ClassMapGen`). It sits between the generated proxies and the native libraries, so it can change behaviour, or even surface, without a `.i` file being touched.
- **Not the contract** — the C++ classes under `MgDev/Common`, `Server` and `Web`. Their shape is free to change as long as the glue above is rebuilt and behaves. The mapagent HTTP API is a wire contract rather than an ABI, and it is documented and tested separately ([docs/openapi.yaml](./docs/openapi.yaml), `test/*.http`).

The pipeline behind all of it starts at `Bindings/src/Bindings/MapGuideApi/MapGuideApiGen.xml` (and `Constants.xml`), which `IMake` (`Bindings/src/IMake`) turns into the SWIG `.i` inputs before SWIG 4.1 emits the proxies and the `*_wrap.cpp` glue. Editing `MapGuideApiGen.xml`, a `.i` file, or a shared fragment under `Bindings/src/SwigCommon/` therefore reaches all three languages at once.

### Which build produces which binding

Both full builds run `cmake_build.sh`, which sets `-DWITH_JAVA=TRUE`, and `Bindings/src/Bindings/CMakeLists.txt` always adds `Php` outside the common subset — so the `ubuntu22` and `generic` full builds both emit the Java and PHP bindings. The .NET glue is built **only** by the extra common-subset pass that `build_mapguide_generic.sh` runs (`--common-subset-only`), and its `mapguideopensource-common-*.tar.gz` is the tarball the Windows build consumes; on Linux that pass compiles the native `*UnmanagedApi` libraries only — the C# proxies are compiled on Windows, as `Bindings/src/Bindings/DotNet/Foundation/CMakeLists.txt` states outright. A `.i` change that reaches the .NET binding is therefore not validated by a Linux-only build.

### Checking a change

1. **The recorded surface.** `Bindings/src/ApiDump/api.java.txt`, `api.dotnet.txt` and `api.php.txt` are per-language dumps of the generated proxies, taken against a live MapGuide installation and reviewed as an SVN diff (`ApiDump/README.txt`). This is MapGuide's counterpart to diffing `nm -D`: it shows whether the surface moved. Like the freeze baselines they are refreshed by hand and are expected to lag the tree, so read them as the last accepted surface rather than as the current one. Beside them, `filelist.*.txt` are `tar -tzf` listings of the shipped installers, which catch a binding library that has stopped being packaged at all.
2. **The interface inputs.** With `MapGuideApiGen.xml`, a `.i` file or `SwigCommon/**` in the change, read the diff for surface movement — a renamed method, a changed parameter type, a class no longer exposed — rather than for C++ correctness.
3. **Behaviour.** `Bindings/src/Test/{DotNet,Java,Php}` exercise the bindings against a running server, and `templates/scripts/container/mapguide_smoke_test.sh` runs a PHP binding sanity check as part of installer verification.
4. **Rebuild the glue.** "The glue still calls the C++ correctly" is only ever true of glue rebuilt against the changed C++, so a C++ edit that this policy permits is still validated by building and running it: build the binding targets in the container that is already running rather than the whole tree — `php_MapGuideApi-4.0.0`, `MapGuideJavaApi-4.0.0`, and the `*UnmanagedApi` libraries in a `--common-subset-only` tree.

An explicit instruction in a task overrides the mode line for that task only, exactly as for FDO (see [Policy gate](#policy-gate-which-mode-are-we-in)): in `freeze` the surface dump in step 1 is the mandatory check for any `mapguide` change that could move the binding API, and a change that would move it is escalated, not made.

## ELF symbol interposition and library init hooks

Interposition is the other way the core/provider boundary surprises you, and it is ELF-only. A symbol with default visibility that more than one shared library in the process defines is resolved by link order, not by which library "owns" it. `libFDO`'s initialiser called a global `_load()` while the GenericRdbms providers defined their own `_load()` as an ELF constructor, so the call could bind to a provider's definition: the geometry package's TLS key was never created and `threadDataKey_S` stayed at its `0` sentinel. The fix was to rename the hooks uniquely (`FdoGeometryThreadDataLoad`) and give them hidden visibility.

- Internal init/teardown hooks get a unique name and hidden visibility. Never introduce a function-scope `extern` with a generic name (`_load`, `_unload`, `init`, `cleanup`) that another library in the process might also define.
- That code must stay inside the non-Windows branch: `__attribute__((constructor))` and `__attribute__((visibility(...)))` are GCC/Clang only, and the Windows build uses `DllMain` instead. An attribute that escapes into the `#ifdef _WIN32` path breaks the MSVC build. The geometry, `Fdo.cpp` and provider hooks are all split this way — keep them split.
- On PE there is no equivalent hazard, because an import is bound to a named DLL. A fix here is not a Windows fix and does not change the Windows export tables.

### #965: the deferred static destructors are harmless — do not try to "fix" them

GCC's default `-fgnu-unique` emits a `STB_GNU_UNIQUE` symbol for vague-linkage data: the `static Fdo…[] = {...}`
tables declared inside member functions in the provider `*Capabilities` headers, and function-local statics in
inline functions such as `fdo::node_generic_mul4::set_empty()::empty` in `Fdo/Unmanaged/Src/Spatial/rtree.h`. As
soon as glibc resolves one it refuses to unload that DSO (`LD_DEBUG=files` prints `activating NODELETE for …` and
never `destroying`), and because `libFDO` holds relocation dependencies on the providers (`… needed by
libFDO-4.2.0.so (relocation dependency)`), one unique symbol pins the whole group. `dlclose()` therefore unloads
nothing and no teardown runs while the process lives. That is ticket #965, and it is not worth fixing:

- The destructors are deferred, not lost — `_dl_fini` runs `.fini_array` and `__cxa_finalize` for every still-loaded
  DSO at process exit, `NODELETE` or not. This is why a post-`dlclose` `/proc/self/maps` check and `LD_DEBUG` are
  the way to see the pinning, and why a suite that still exits `OK` is no evidence that teardown ran.
- What they release is bounded process-lifetime state (sqlite3's optional global init, one 56-byte `ProjConverter`,
  GDAL's driver manager, one pthread key/mutex per GenericRdbms provider), and the DSO is never reloaded, so
  nothing goes stale and nothing grows unboundedly.
- LeakSanitizer is unaffected either way: its check runs before `_dl_fini`, so those frees never reach the report.
- The `__attribute__((destructor))` teardown the ticket proposes does nothing on its own — the same pinning defeats
  it — and would run the teardown *twice* at exit, because both callbacks are exit-time on Linux.
- Forcing the unload (`-fno-gnu-unique`) was measured and is harmful: `libWMSProvider` segfaults on `dlclose()`
  (GDAL register-then-destroy followed by unloading libgdal; reproducible from a libgdal-only DSO), and the OGR
  suite gains a leak record and a second static init. Do not re-attempt it. The "register-then-destroy" half is
  now gone — the WMS provider no longer calls `GDALDestroyDriverManager()`, which was also a heap-use-after-free
  at ordinary process exit; see [docs/fdo-exit-teardown.md](./docs/fdo-exit-teardown.md).

This conclusion is about **vague-linkage data being pinned**, and it does not generalise to every exit-time
destructor. A teardown that reads state owned by *another static in the same library* is a real
static-destruction-order bug and is worth fixing — that is what happened when `~FdoConnectionManager` walked
`m_moduleMap` from `DllMain`/`InitClass` teardown, hanging or segfaulting ~14% of test runs after the tests had
already passed. See [docs/fdo-exit-teardown.md](./docs/fdo-exit-teardown.md) for the stack, the fix and the
100-run A/B measurement.

## Code style guidelines (shell)

1. **Container engine** — source `./container_engine.sh` and use `$DOCKER_CMD` (plus `$DOCKER_RUN_EX_ARGS`, `$DOCKER_VOLUME_OPT`, `$DOCKER_RUN_AS_ROOT_ARGS`). Never hardcode `docker` or `podman`. Append `$DOCKER_VOLUME_OPT` to **every** host-path `-v` mount. It is `:z` (shared SELinux label) when SELinux is enforcing, because the same tree is mounted by the build, test, installer and interactive containers: a private (`:Z`) label can only be held by one container at a time, so a second `:Z` mount relabels the tree and any container already running loses access to its own mounts (`EACCES`/`Permission denied`, even as root, since `CAP_DAC_OVERRIDE` does not bypass SELinux). A force-created `:Z` will break a running interactive container for as long as the shared label is not restored (`podman unshare chcon -R -t container_file_t -l s0 <tree>`).
2. **Argument parsing** — `while [ $# -gt 0 ]` + `case "$1"` + `shift`. Options that take a value consume `$2` and shift again.
3. **Output indentation** — use the `indent()` helper (`sed 's/^/    /'`) and pipe verbose tool output through `| indent`.
4. **Error handling** — no `set -e`. Use explicit checks: `check_build()` or `if [ "$?" -ne 0 ]` after each build invocation, then `exit 1`.
5. **Naming** — `FDO_VER_MAJOR/MINOR/REL/REV`, `FDO_VER`, `FDO_VER_TRIPLE`; same shape for `MG_VER_*`. `BUILD_CONF` is `Release` or `Debug`. `distro_label` is `distro` + major tag (`ubuntu22`) or `generic`. `cpu_label` is `amd64` or `i386`.
6. **Shebangs** — new scripts use `#!/bin/bash`. Keep existing `#!/bin/sh` scripts POSIX-compatible unless you are already editing them.

## Code style guidelines (C++)

See [CPP_STYLE.md](./CPP_STYLE.md) — applies to edits under `MgDev` and `fdo`.

## Common patterns

- **Generation** — `env_setup.sh` writes a `Dockerfile` and copies the matching `snap.sh` into `docker/<cpu>/<target>/<distro_label>/{run,develop_thin,build}`. Edit `templates/**`, then regenerate.
- **Image layering** — `run` (base + runtime deps) → `develop_thin` (build deps, no source) → `build` (build steps baked in; `ADD`s the FDO SDK tarball, `atomic.h`, and the binary-stripping script).
- **Distro overrides** — a `templates/distros/<distro>/<name>_<distro_label>.txt` (or `install_<distro>.sh`) is picked up automatically and falls back to `<name>.txt`. Examples: `cmd_prepare_mapguide_develop_ubuntu22.txt`, `args_fdo_build_generic.txt`, `dockerfile_x64_mapguide_build_<label>.txt`.
- **Thirdparty libraries** — `generic` builds internal copies; `ubuntu22` uses system packages. See the matrix tables in `README.md`.
- **Version scripts** — `fdo_version.sh` and `mapguide_version.sh` are generated by `env_setup.sh` from `svn info` and are gitignored. Never hand-edit or commit them.

## Validation (definition of done)

- **Shell/template-only changes** — run `bash -n` (or `sh -n`) on every touched script. If `templates/**` changed, re-run `env_setup.sh` and review the regenerated Dockerfiles. Also check `git status` for files the scripts wrote outside the gitignored paths.
- **Source-tree changes (`MgDev` or `fdo`)** — a run of `./build_thin.sh` against the **baseline distro** is the required validation. The baseline distro is the latest Ubuntu version supported by the build scripts (currently 22.04).
- **Release vs Debug** — a Debug (ASan) pass does not validate the Release build. Release's optimiser assumes `this` is never NULL and deletes the NULL guards that Debug's `-O0` keeps, so a suite can pass in Debug and segfault in Release; run the affected suite in **both** configurations. See the NULL-`this` note in [CPP_STYLE.md](./CPP_STYLE.md).
- **Shipped-header changes** — check the [current mode](#current-cycle) first. A change to a header the SDK installs can move the provider-facing ABI; see [FDO API/ABI compatibility](#fdo-apiabi-compatibility) for how to rule it in or out. For `mapguide` the equivalent question is whether the binding surface moved, not whether a C++ class did; see [MapGuide API/ABI compatibility](#mapguide-apiabi-compatibility).
- **Container-based validation** — run it in the container that is already running for that target and build configuration (`$DOCKER_CMD exec`), not in a freshly started one; see [Running commands inside build containers](#running-commands-inside-build-containers).
- **Memory-leak fixes** — a full run of the affected suite in the baseline Debug container, reporting the before/after leak totals and the direct-record count, plus an update to the matching `docs/*memory-leaks.md`. For MapGuide the suite is the whole server (`run_mapguide_tests.sh --component all`); a clean single-suite run is not the same evidence, because each process's exit-time races are different. See [Debugging memory leaks](#debugging-memory-leaks-asanlsan).
- **Locking/thread-safety changes** — reproduce the failure first (a deadlock proves itself: single-threaded process, no CPU, waiting in `futex_do_wait`), then show the affected suite green. A lock that only exists for Windows cannot be signed off by reading the diff, because the two platforms do not share the semantics being changed — see **Platform locking semantics** above.
- **Thread-lifecycle or server-shutdown changes** (`MgThreadBase`, the pools, `MgServer::fini()`, accept handlers) — `run_mapguide_tests.sh --run-mode` in the baseline container as well as `--component all`: the suites never enter `MgServer::svc()`'s reactor branch, so a shutdown hang or a leak in that branch is invisible to them.
- Full builds are expensive and are not required for every change — use them only when build logic changed or as verification for source-tree edits.
- Before committing or pushing, re-run the validation relevant to the files you touched.

## Known issues

- **ASLR/ASAN on Ubuntu 22.04 hosts** — set `sudo sysctl vm.mmap_rnd_bits=28` before building; see `README.md` for details.
- **WSL2** — use Docker Desktop; Rancher Desktop is not suitable.
- **`env_test_thin.sh` may be flaky** — prefer an interactive build container for debugging.
- **The WFS and WMS suites query live public servers** (for example `services.ga.gov.au`, `services.land.vic.gov.au`), so treat their failures as environmental until a change in the tree is proven to be the cause.
- MapGuide has not been tested on Ubuntu versions older than 22.04.
- 32-bit (`x86`) Linux builds are not supported.
- `make_installer.sh` requires `makeself` at `~/makeself`.
